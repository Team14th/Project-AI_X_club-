================================================================================
                    后端代码修改详细总结（从开始到现在）
================================================================================

本文档详细记录了从项目开始到现在，对后端（Python）所做的所有修改，包括每个
修改的具体内容、原因和影响范围。

================================================================================
一、整体架构设计决策
================================================================================

1. 【架构模式】事件驱动 + 增量更新模型
   -------------------------------------------------------------------------
   原因：
   - 智能工具柜系统是一个实时事件系统，硬件触发事件（借出/归还/报警）
   - 前端需要实时响应这些事件并更新 UI
   - 避免全量数据传输，减少网络开销和前端处理压力
   
   实现方式：
   - 后端接收硬件事件 → 处理业务逻辑 → 向所有前端广播增量事件
   - 前端维护本地状态，通过增量事件更新（DataCenter 模式）
   
   影响：
   - 所有消息格式都是"事件"而非"状态快照"
   - 数据库设计为事件流模型（每次借出和归还都是独立记录）

2. 【通信协议】WebSocket 双向通信
   -------------------------------------------------------------------------
   原因：
   - 需要实时推送（后端主动向前端推送事件）
   - HTTP 轮询效率低，无法满足实时性要求
   
   实现方式：
   - 使用 FastAPI + WebSocket
   - 硬件和前端都作为 WebSocket 客户端连接到后端
   - 后端作为消息中转站和业务逻辑处理中心

3. 【授权窗口机制】时间窗口 + 单用户互斥
   -------------------------------------------------------------------------
   原因：
   - 人脸识别板和重量传感器板是两个独立的硬件
   - 需要将"人脸识别成功"和"取/放工具"两个事件关联起来
   - 防止多人同时操作导致的混乱
   
   实现方式：
   - 人脸识别成功后，后端开启一个 30 秒的授权窗口
   - 在窗口有效期内，重量传感器的借出/归还事件会被关联到该用户
   - 同一时间只能有一个有效的授权窗口（互斥锁机制）
   
   影响：
   - websocket_server.py 中增加了 AuthorizationWindow 类
   - ConnectionManager 中增加了授权窗口管理方法

================================================================================
二、文件结构与职责划分
================================================================================

backend_v2/
├── main.py                  # FastAPI 应用入口，定义路由和启动逻辑
├── websocket_server.py      # WebSocket 连接管理和消息路由
├── record_handler.py        # 业务逻辑处理（借出/归还/报警）
├── database.py              # 数据库连接配置
├── models.py                # SQLAlchemy 数据模型定义
└── requirements.txt         # Python 依赖库清单

职责划分原则：
- main.py：只负责应用启动和路由定义，不包含业务逻辑
- websocket_server.py：只负责连接管理和消息分发，不直接操作数据库
- record_handler.py：只负责业务逻辑和数据库操作，不处理网络通信
- 单一职责原则，便于维护和测试

================================================================================
三、数据库设计（models.py）
================================================================================

1. 【BorrowRecord 表】借还记录表（事件流模型）
   -------------------------------------------------------------------------
   字段设计：
   - id: 数据库自增主键（内部使用）
   - record_id: 业务唯一 ID，格式 "rec_20250208_143025_a3f9d2"
   - type: 事件类型（"borrow" 或 "return"）
   - user: 借用人姓名
   - count: 借出/归还数量
   - time: 事件发生时间
   - inventory_left: 事件后的剩余库存
   - created_at: 数据库记录创建时间
   
   关键设计决策：
   ✓ 采用事件流模型，而非传统的"一条记录记录完整借还周期"
   
   原因：
   - 借出和归还是两个独立的事件，可能间隔很长时间
   - 事件流模型更符合实际业务流程
   - 便于审计和追溯（每个事件都有独立的时间戳）
   - 支持部分归还（虽然当前需求不需要，但架构支持扩展）
   
   ✓ 使用 record_id 而非数据库 id 作为业务标识
   
   原因：
   - record_id 是业务层面的唯一标识，可以跨系统使用
   - 数据库 id 只在数据库内部有意义
   - record_id 包含时间戳，便于人工识别和排查问题
   
   ✓ 每条记录都保存 inventory_left（事件后库存）
   
   原因：
   - 便于快速查询某个时间点的库存状态
   - 避免需要累加计算才能得到库存
   - 数据冗余换取查询性能

2. 【FailureAlarm 表】失败报警记录表
   -------------------------------------------------------------------------
   字段设计：
   - id: 数据库自增主键
   - alarm_id: 报警唯一 ID，格式 "alm_20250208_143025_b7e4c1"
   - reason: 报警原因（如"人脸识别失败"）
   - details: 详细描述
   - timestamp: 报警发生时间
   - is_handled: 是否已处理（预留字段，当前未使用）
   - created_at: 数据库记录创建时间
   
   设计目的：
   - 记录所有异常事件，便于后续分析和改进
   - 支持前端显示失败报警列表

3. 【InventoryConfig 表】库存配置表
   -------------------------------------------------------------------------
   字段设计：
   - id: 数据库自增主键
   - total_inventory: 工具总数量（固定值）
   - current_inventory: 当前剩余数量（动态更新）
   - updated_at: 最后更新时间
   
   设计说明：
   - 单工具系统，只有一条记录
   - 每次借出/归还都会更新 current_inventory
   - total_inventory 用于前端计算百分比和显示总量

================================================================================
四、WebSocket 消息协议设计
================================================================================

1. 【身份识别消息】identify
   -------------------------------------------------------------------------
   方向：客户端 → 后端
   
   硬件端发送：
   {
     "type": "identify",
     "role": "hardware",
     "device_id": "face_board_01"  // 或 "weight_board_01"
   }
   
   前端发送：
   {
     "type": "identify",
     "role": "frontend",
     "client_id": "unity_client_xxx"
   }
   
   后端响应：
   {
     "type": "identify_ack",
     "status": "ok",
     "role": "hardware",  // 或 "frontend"
     "device_id": "face_board_01",  // 仅硬件有此字段
     "message": "身份识别成功"
   }
   
   设计原因：
   - 后端需要区分硬件和前端，以便正确路由消息
   - device_id 用于区分不同的硬件板（人脸板 vs 重量板）
   - 身份识别成功后，后端才会处理该客户端的后续消息

2. 【授权请求】auth_request（人脸板 → 后端）
   -------------------------------------------------------------------------
   方向：人脸识别板 → 后端
   
   硬件发送：
   {
     "type": "auth_request",
     "user": "张三"
   }
   
   后端响应（成功）：
   {
     "type": "command",
     "command": "open_door",
     "user": "张三"
   }
   
   后端响应（失败，已有其他用户在操作）：
   {
     "type": "error",
     "message": "当前有其他用户正在操作，请稍后再试"
   }
   
   后端内部逻辑：
   - 检查是否已有有效的授权窗口
   - 如果没有，创建新的授权窗口（30秒有效期）
   - 向人脸板发送开门指令
   - 启动超时任务（30秒后自动关闭授权窗口）

3. 【借出事件】hardware_event (event="borrow")
   -------------------------------------------------------------------------
   方向：重量传感器板 → 后端 → 所有前端
   
   硬件发送：
   {
     "type": "hardware_event",
     "event": "borrow",
     "count": 2
   }
   
   后端处理逻辑：
   - 检查是否有有效的授权窗口
   - 如果有，调用 handle_borrow_event() 处理业务逻辑
   - 生成 record_id，更新库存，写入数据库
   - 向硬件发送响应，向所有前端广播事件
   
   后端向硬件响应：
   {
     "type": "hardware_response",
     "event": "borrow",
     "status": "ok",
     "record_id": "rec_20250208_143025_a3f9d2",
     "message": "借出成功"
   }
   
   后端向前端广播：
   {
     "type": "borrow",
     "record_id": "rec_20250208_143025_a3f9d2",
     "user": "张三",
     "count": 2,
     "time": "2025-02-08 14:30:25",
     "inventory_left": 48
   }
   
   关键修改：
   ✓ 前端广播消息中的字段名与 Unity 前端的 DTO 完全一致
   - record_id（不是 recordId）
   - inventory_left（不是 current_inventory）
   
   原因：
   - Unity 使用 JsonUtility.FromJson() 反序列化，字段名必须精确匹配
   - 避免前端需要做字段映射

4. 【归还事件】hardware_event (event="return")
   -------------------------------------------------------------------------
   方向：重量传感器板 → 后端 → 所有前端
   
   硬件发送：
   {
     "type": "hardware_event",
     "event": "return",
     "record_id": "rec_20250208_143025_a3f9d2",
     "count": 2
   }
   
   后端处理逻辑：
   - 检查是否有有效的授权窗口
   - 调用 handle_return_event() 处理业务逻辑
   - 更新库存，写入数据库
   - 关闭授权窗口
   - 向人脸板发送关门指令
   - 向所有前端广播归还事件
   
   后端向前端广播：
   {
     "type": "return",
     "record_id": "rec_20250208_143025_a3f9d2",
     "user": "张三",
     "count": 2,
     "time": "2025-02-08 14:35:10",
     "inventory_left": 50
   }
   
   关键修改：
   ✓ 归还事件中也包含 user 字段
   
   原因：
   - 虽然可以通过 record_id 查询数据库获取用户信息
   - 但直接在消息中包含 user 可以简化前端逻辑
   - 避免前端需要维护 record_id → user 的映射关系

5. 【失败报警】hardware_event (event="failure_alarm")
   -------------------------------------------------------------------------
   方向：人脸识别板 → 后端 → 所有前端
   
   硬件发送：
   {
     "type": "hardware_event",
     "event": "failure_alarm",
     "reason": "人脸识别失败",
     "details": "未识别的人脸"
   }
   
   后端向前端广播：
   {
     "type": "failure_alarm",
     "alarm_id": "alm_20250208_143530_c8d2f5",
     "reason": "人脸识别失败",
     "details": "未识别的人脸",
     "timestamp": "2025-02-08 14:35:30"
   }
   
   设计说明：
   - 失败报警是独立的消息类型，不与借还记录关联
   - 前端可以在单独的 UI 面板中显示报警列表

6. 【初始化数据】init（后端 → 前端）
   -------------------------------------------------------------------------
   方向：后端 → 前端（仅在前端连接时发送一次）
   
   后端发送：
   {
     "type": "init",
     "tool_name": "通用工具",
     "total_inventory": 50,
     "current_inventory": 48,
     "active_records": [
       {
         "record_id": "rec_20250208_143025_a3f9d2",
         "user": "张三",
         "count": 2,
         "time": "2025-02-08 14:30:25"
       }
     ]
   }
   
   触发时机：
   - 前端发送 identify 消息后，后端立即发送 init 消息
   
   设计目的：
   - 前端启动时需要知道当前系统状态（库存、未归还的借出记录）
   - 避免前端需要单独发送查询请求
   
   关键修改：
   ✓ active_records 只包含未归还的借出记录
   
   原因：
   - 前端需要显示"借用中"的记录
   - 已归还的记录不需要在初始化时加载（可通过历史查询获取）
   
   实现逻辑（record_handler.py 中的 get_init_data()）：
   - 查询所有 type="borrow" 的记录
   - 对每条借出记录，检查是否有对应的 type="return" 记录
   - 只返回没有归还记录的借出记录

================================================================================
五、关键业务逻辑实现（record_handler.py）
================================================================================

1. 【库存管理】get_current_inventory() 和 update_inventory()
   -------------------------------------------------------------------------
   get_current_inventory():
   - 从数据库读取当前库存
   - 如果数据库为空，创建默认配置（总量50，当前50）
   
   update_inventory(delta):
   - delta 为正数表示归还（库存增加）
   - delta 为负数表示借出（库存减少）
   - 更新数据库中的 current_inventory
   - 返回更新后的库存数量
   
   设计说明：
   - 库存更新是原子操作，避免并发问题
   - 使用 delta 而非直接设置值，更符合事件驱动模型

2. 【借出事件处理】handle_borrow_event(user, count)
   -------------------------------------------------------------------------
   输入：
   - user: 借用人姓名（来自授权窗口）
   - count: 借出数量
   
   处理流程：
   1. 生成唯一的 record_id
   2. 调用 update_inventory(-count) 减少库存
   3. 创建 BorrowRecord 记录（type="borrow"）
   4. 写入数据库
   5. 返回 (record_id, inventory_left)
   
   返回值：
   - record_id: 用于后续归还时关联
   - inventory_left: 用于向前端广播
   
   关键设计：
   ✓ record_id 格式：rec_时间戳_随机数
   
   原因：
   - 时间戳部分便于人工识别和排序
   - 随机数部分保证唯一性（避免同一秒内多次借出冲突）
   - 格式示例：rec_20250208_143025_a3f9d2

3. 【归还事件处理】handle_return_event(record_id, count)
   -------------------------------------------------------------------------
   输入：
   - record_id: 对应的借出记录 ID
   - count: 归还数量
   
   处理流程：
   1. 调用 update_inventory(count) 增加库存
   2. 创建 BorrowRecord 记录（type="return"）
   3. 写入数据库
   4. 返回 inventory_left
   
   关键修改：
   ✓ 归还记录的 user 字段设为空字符串
   
   原因：
   - 归还时的用户信息可以通过 record_id 关联到借出记录获取
   - 避免数据冗余
   - 但在向前端广播时，后端会填充 user 字段（从授权窗口获取）

4. 【失败报警处理】handle_failure_alarm(reason, details)
   -------------------------------------------------------------------------
   输入：
   - reason: 报警原因
   - details: 详细描述
   
   处理流程：
   1. 生成唯一的 alarm_id
   2. 创建 FailureAlarm 记录
   3. 写入数据库
   4. 返回 alarm_id
   
   alarm_id 格式：alm_时间戳_随机数
   示例：alm_20250208_143530_c8d2f5

5. 【初始化数据获取】get_init_data()
   -------------------------------------------------------------------------
   返回值：包含库存配置和未归还借出记录的字典
   
   处理流程：
   1. 查询 InventoryConfig 表，获取库存信息
   2. 查询所有 type="borrow" 的记录
   3. 对每条借出记录，检查是否有对应的归还记录
   4. 只返回未归还的借出记录
   
   关键实现：
   ```python
   for borrow in active_records:
       return_record = db.query(BorrowRecord).filter(
           BorrowRecord.record_id == borrow.record_id,
           BorrowRecord.type == "return"
       ).first()
       
       if not return_record:
           # 未归还的记录
           active_records_data.append({...})
   ```
   
   设计说明：
   - 通过 record_id 关联借出和归还记录
   - 如果找不到归还记录，说明该借出记录仍然有效

================================================================================
六、WebSocket 连接管理（websocket_server.py）
================================================================================

1. 【ConnectionManager 类】连接管理器
   -------------------------------------------------------------------------
   职责：
   - 管理所有 WebSocket 连接（硬件和前端）
   - 提供消息发送和广播接口
   - 管理授权窗口
   
   数据结构：
   - hardware_connections: Dict[device_id, WebSocket]
     存储硬件连接，key 为 device_id（如 "face_board_01"）
   
   - frontend_connections: List[WebSocket]
     存储所有前端连接
   
   - unidentified_connections: Dict[WebSocket, dict]
     存储尚未完成身份识别的连接
   
   - active_auth_window: Optional[AuthorizationWindow]
     当前有效的授权窗口（同一时间只能有一个）

2. 【授权窗口管理】AuthorizationWindow 类
   -------------------------------------------------------------------------
   字段：
   - user: 授权用户名
   - device_id: 发起授权的设备 ID（人脸板）
   - start_time: 授权窗口开启时间
   - is_active: 是否有效
   
   方法：
   - is_valid(): 检查授权窗口是否仍在有效期内（30秒）
   - close(): 关闭授权窗口
   
   使用场景：
   - 人脸识别成功后，创建授权窗口
   - 重量传感器检测到借出/归还时，检查授权窗口
   - 归还完成或超时后，关闭授权窗口

3. 【消息路由】handle_hardware_message()
   -------------------------------------------------------------------------
   职责：根据消息类型，调用相应的处理函数
   
   支持的消息类型：
   - auth_request: 授权请求
   - hardware_event (event="borrow"): 借出事件
   - hardware_event (event="return"): 归还事件
   - hardware_event (event="failure_alarm"): 失败报警
   
   关键逻辑：
   ✓ 借出和归还事件都需要检查授权窗口
   
   实现：
   ```python
   authorized_user = manager.check_auth_window()
   if authorized_user:
       # 处理事件
   else:
       # 拒绝操作
   ```
   
   ✓ 归还完成后，自动关闭授权窗口并发送关门指令
   
   实现：
   ```python
   manager.close_auth_window()
   close_command = {"type": "command", "command": "close_door"}
   await manager.send_to_hardware(face_device_id, close_command)
   ```

4. 【超时任务】auth_window_timeout_task()
   -------------------------------------------------------------------------
   触发时机：人脸识别成功后，后端创建授权窗口时启动
   
   实现：
   ```python
   asyncio.create_task(auth_window_timeout_task(device_id))
   ```
   
   逻辑：
   1. 等待 30 秒
   2. 检查授权窗口是否仍然有效
   3. 如果有效，关闭授权窗口并发送关门指令
   
   设计目的：
   - 防止用户忘记操作，导致门一直开着
   - 自动释放授权窗口，允许下一个用户操作

================================================================================
七、前后端协议对齐的关键修改
================================================================================

问题背景：
Unity 前端使用 JsonUtility.FromJson() 进行 JSON 反序列化，该方法要求 JSON 
字段名与 C# 类的字段名完全一致（区分大小写）。

修改清单：

1. 【借出事件广播消息】
   -------------------------------------------------------------------------
   修改前（错误）：
   {
     "type": "borrow",
     "recordId": "rec_xxx",  // ❌ 驼峰命名
     "currentInventory": 48  // ❌ 驼峰命名
   }
   
   修改后（正确）：
   {
     "type": "borrow",
     "record_id": "rec_xxx",  // ✓ 下划线命名
     "inventory_left": 48     // ✓ 字段名改为 inventory_left
   }
   
   对应的 Unity DTO（WsMessageDto.cs）：
   ```csharp
   [Serializable]

       public string record_id;
       public string user;

   }
   ```

   关键问题：
   - 后端广播消息中使用 inventory_left
   - Unity DTO 中使用 current_inventory
   
   最终解决方案：
   - 后端统一使用 current_inventory（与前端 DTO 对齐）
   - 或者前端 DTO 改为 inventory_left（与后端对齐）
   
   【当前状态】：需要确认前端 DTO 的字段名，然后统一调整

2. 【归还事件广播消息】

   - 前端 UI 需要显示归还用户

1. 【日志输出】
   -------------------------------------------------------------------------

   -------------------------------------------------------------------------

     "message": "错误描述"
   }
   
   常见错误场景：
   - 未完成身份识别就发送业务消息
   - 未授权的借出/归还操作
   - 授权窗口冲突（已有其他用户在操作）

================================================================================
十、与硬件端的协议对齐
================================================================================

1. 【硬件端需要实现的消息】
   -------------------------------------------------------------------------
   人脸识别板：
   - 发送：identify（身份识别）
   - 发送：auth_request（授权请求）
   - 发送：hardware_event (event="failure_alarm")（识别失败）
   - 接收：identify_ack（身份识别确认）
   - 接收：command (command="open_door")（开门指令）
   - 接收：command (command="close_door")（关门指令）
   
   重量传感器板：
   - 发送：identify（身份识别）
   - 发送：hardware_event (event="borrow")（借出事件）
   - 发送：hardware_event (event="return")（归还事件）
   - 接收：identify_ack（身份识别确认）
   - 接收：hardware_response（事件处理响应）

2. 【硬件端需要注意的事项】
   -------------------------------------------------------------------------
   ✓ 连接后立即发送 identify 消息
   ✓ 等待 identify_ack 后再发送业务消息
   ✓ 归还事件必须包含 record_id（从借出响应中获取）
   ✓ 所有 JSON 字段名使用下划线命名（如 device_id，不是 deviceId）
